# openJiuwen 各仓资料体系治理规范

本规范针对 openJiuwen 各代码仓的资料体系（含 README、docs、examples、目录结构等）提供规范要求，确保各仓资料达到"新用户 30 分钟跑通、老用户查得准、贡献者照模板写"的水平。

各 SIG 在开展资料体系治理前，请先阅读本规范，参照相应要求执行。配套模板请参见 [模板目录](template/)。

> **说明：**
> 本规范的内容分为【规则】、【建议】两类：
> - 【规则】表示规范要求，必须遵从。
> - 【建议】表示参考建议，可选遵从。

## 治理目标

让各仓文档从"有"达到"齐"：

- 有（现状）：各仓均有 README、多数仓有 docs 内容。
- 齐（目标）：每仓文档标准化达标——README 结构规范完整、docs 具备高检索性、目录层级清晰合理、内容表述精炼、新用户可零障碍完成部署运行。

### 原则：以代码仓为权威源

GitCode 各仓的 docs 目录是 openJiuwen 文档的唯一权威来源。官网（openjiuwen.com）仅作为展示层单向引用代码仓内容，不能反向引用。各仓 README 的指引链接必须指向仓内 docs，不得直接跳转至官网。

## README 规范

README 仅做"最小闭环"展示，保持精简、提供核心指引。深度技术内容统一交由 docs 承载，确保 README 与 docs 各司其职、互不重复。

### README 七段结构

【规则】README 必须包含以下七段内容，按顺序组织：

| 序号 | 段落 | 类型 | 规范要求 |
| -------- | -------- | -------- | -------- |
| 1 | 项目定位 | 必有 | 项目名加一句话定位，不超过一行说清"是什么" |
| 2 | 核心特性 | 必有 | 提炼三至五条，解答"为什么用它" |
| 3 | 相关文档 | 必有 | 极简链接段落，指向仓内 docs、examples、CHANGELOG 等，不超过四至五行 |
| 4 | 环境要求 | 必有 | 明确列出运行前置条件，含 OS、语言版本、依赖 |
| 5 | 安装指南 | 必有 | 提供极简安装命令，支持 pip、mvn、docker 等 |
| 6 | Quick Start | 必有 | 提供"复制即跑"的示例代码 |
| 7 | License | 必有 | 明确标注开源许可证 |

【建议】README 可包含以下扩展模块：Badges（状态徽章）、详细用法、架构设计、配置说明。

【规则】如仓无独立 CHANGELOG.md，必须通过 GitCode Release 功能管理版本更新信息，并在 README 中呈现 Release 查看入口链接。

【规则】相关文档段落必须指向仓内路径，不得直接跳转至官网。

| 正例 | 反例 |
| -------- | -------- |
| [文档](../sigs/) | 更多内容请访问官网 |
| [快速开始](../README.md) | [快速开始](https://openjiuwen.com/quick-start) |

【规则】环境要求中的版本号必须与 pom.xml、pyproject.toml、package.json 等构建文件中的实际值一致。

> **注意：**
> 多语言 README 中的版本号、环境要求等关键参数必须保持一致。中文为权威源，英文跟随。建议通过 CI 脚本校验 README 与构建文件中的硬编码数值是否一致。

【规则】Quick Start 示例代码必须可直接复制运行，不得仅包含占位符。

| 正例 | 反例 |
| -------- | -------- |
| 配置区标注 `# 请替换为你的 API Key`，其余代码完整可运行 | 全篇 `MODEL_PROVIDER = "xxxx"`、`API_KEY = "xxxx"` 占位符，无法直接运行 |

【规则】如有双语 README，中文为权威源（README.md 或 README.zh.md），英文跟随（README.en.md 或 README.md）。两份内容必须参数一致、结构对称。

> **说明：**
> 建议参考 [README 模板](template/README-template.md) 进行写作。

## docs 四类框架

docs 按读者意图归入 Tutorial、How-to、Reference、Explanation 四类框架。缺一类即结构缺口。

### 四类定义

| 类别 | 读者意图 | 写作方式 | 对应内容 |
| -------- | -------- | -------- | -------- |
| Tutorial（教程） | 带新手入门，"跟着我做一遍" | 按步骤引导完成一个具体任务，侧重学习 | 快速上手、第一个 Agent |
| How-to（操作指南） | 解决具体任务，"我要做 X 怎么做" | 按步骤解决一个已知问题，侧重完成 | 配置 MCP、部署服务、接入协议 |
| Reference（参考） | 查 API 或配置，"这个参数什么意思" | 事实性描述，结构化、可检索 | API 文档、配置参数表、错误码表 |
| Explanation（解释） | 讲为什么这样设计，"它原理是什么" | 解释概念、架构、设计决策 | 架构概述、设计决策、关键概念 |

### 归类规则

【规则】每篇文档应明确归属一个类别。同一篇文档不得混合多个类别。

【规则】四类文档应分目录存放，目录名即类别名。

| 正例 | 反例 |
| -------- | -------- |
| docs/zh/tutorial/quick-start.md<br>docs/zh/how-to/configure-mcp.md<br>docs/zh/reference/api.md<br>docs/zh/explanation/architecture.md | docs/zh/高阶用法/（混合 How-to、Explanation、Tutorial）<br>docs/zh/2.开发指南/（按编号排列，不按意图分类） |

【规则】Tutorial 类文档使用数字前缀编号（01-、02-），表示推荐阅读顺序。How-to、Reference、Explanation 类文档使用语义名，不编号。

| 正例 | 反例 |
| -------- | -------- |
| tutorial/01-quick-start.md<br>tutorial/02-first-agent.md<br>how-to/configure-mcp.md<br>reference/api.md | tutorial/快速开始.md（无编号）<br>how-to/1.配置MCP.md（不应编号） |

【规则】SDK 仓的 Reference 为类级 API 文档（方法签名、参数、返回值）。服务仓的 Reference 为 REST API 参考（端点、请求体、响应体、错误码）。

> **说明：**
> SDK 仓用户通过 import 使用框架，Reference 重点是"查类的方法签名"。服务仓用户通过 HTTP 调用接口，Reference 重点是"查接口的请求响应格式"。两者读者不同、查阅场景不同，文档形态也不同。

【建议】服务仓的 Reference 采用双轨并行：docs 中放精简版 REST API 参考（核心接口加典型请求响应示例），完整版由服务运行时 OpenAPI 自动生成并在 docs 中链接。

【建议】docs/README.md 作为文档介绍与导航入口，简要说明文档覆盖范围和阅读建议，并按四类列出文档链接。当某一类别文档数量超过 10 篇时，再在该类别目录下新建 README.md 做栏目级导航。

## 目录组织

### 目录结构

【规则】各仓应遵循以下目录结构：

```
仓根/
├── README.md              # 最小闭环：定位 / 特性 / 相关文档 / 环境 / 安装 / QuickStart / License
├── LICENSE                #
├── CHANGELOG.md           # 可选：变更日志（如版本更新信息）；可通过 GitCode Release 功能管理，但必须在 README 中呈现 Release 查看入口
├── CONTRIBUTING.md        # 贡献指南
├── SECURITY.md            # 可选：安全策略（如漏洞报告指南）；参考：https://gitcode.com/openJiuwen/skillhub/blob/develop/SECURITY.md
├── examples/              # 可运行示例工程（clone 即跑）
├── docs/                  # 用户文档（给用户读，Diátaxis 四类）
│   ├── zh/                # 中文权威源
│   │   ├── tutorial/      # 教程：使用 01-、02- 等数字前缀
│   │   ├── how-to/        # 操作指南：使用语义化名称，不编号
│   │   ├── reference/     # 参考文档（如 API 文档）：使用语义化名称，不编号
│   │   └── explanation/  # 解释文档（如原理介绍）：使用语义化名称，不编号
│   ├── en/                # 英文跟随
│   └── README.md          # 文档介绍与导航入口；参考：https://gitcode.com/openJiuwen/jiuwenswarm/blob/develop/docs/README.md
└── design/                # 可选：开发设计稿（给开发者；如涉及架构机制等请归档此处，不要放入 docs）
```

> **说明：**
> 备注中标注为"可选"的文件或目录，表示在有必要时包含即可，不要求必须存在。

### 目录六规则

【规则】编号：Tutorial 类文档使用数字前缀编号（01-、02-），表示推荐阅读顺序。其余类别不编号。

【规则】归位：docs 与 design 分离。设计稿、开发内部文档放入 design/ 目录（如有），不混进 docs/。临时文件（如 .tmp、.bak）不得提交到仓库。

【规则】命名：文件名使用 kebab-case（全小写，单词间用中划线连接），语义化，不超过四个英文单词。同仓内风格统一即合规。

| 正例 | 反例 |
| -------- | -------- |
| quick-start.md<br>configure-mcp.md<br>architecture-overview.md | 快速开始.md（中文文件名）<br>ConfigureMCP.md（驼峰大写）<br>notes.tmp（临时文件残留） |

【规则】一文件一主题：一篇文档只覆盖一个主题。如一篇文档标题数超过 20 个，应拆分为多篇独立文档。

【规则】双语：中文为权威源，英文跟随。docs/zh/ 为中文，docs/en/ 为英文，两份目录结构应对称。

【规则】LICENSE 放在仓根目录。

### documents 改名

【规则】如仓当前使用 `documents/` 目录名，应统一改名为 `docs/`。

> **注意：**
> 改名后需同步更新 README 中的相关文档链接和所有内部交叉引用。

### 内部设计文档归位

【规则】开发设计稿、架构设计文档放入 `design/` 目录（如仓有此类文档），不混进 `docs/`。如文档已存在于源码目录内（如 `management/session/DESIGN.md`），应在 docs 的 Explanation 类别中添加链接指向它，使其可被导航发现。

| 正例 | 反例 |
| -------- | -------- |
| design/session-vcs.md（移入 design 目录）<br>docs/zh/explanation/ 中链接到 design/session-vcs.md | docs/dev/session/vcs_design_cn.md（不在导航体系中）<br>management/session/DESIGN.md（藏在源码目录深处，无法通过导航发现） |

## 落地目标卡

各仓文档达标需满足以下五条：

### 最小闭环

【规则】安装加 Quick Start 加 examples 示例工程三件套齐全。用户 clone 仓后可在 30 分钟内跑通。

### README 七段

【规则】定位、特性、相关文档、环境、安装、Quick Start、License 七段齐全。

### docs 四类

【规则】Tutorial、How-to、Reference、Explanation 四类目录齐全。缺一类即结构缺口。

### 目录六规则

【规则】编号、归位、命名、一文件一主题、双语、LICENSE 仓根六规则达标。

### 质量加成

【建议】文档内容应满足以下质量指标：

- 体量：单篇文档平均字节合理，避免"少而长"（单篇过大）或"多而碎"（单篇过小）两种极端。
- 准：API 文档覆盖率不低于 80%（已覆盖公开 API 类数 / 公开 API 类总数）。
- 新：文档最后更新时间与代码最后提交时间间隔不超过 30 天。
- 经实测：每仓应有 3 至 5 名新用户完成"30 分钟跑通"实测。

## 迁移路径

各 SIG 拿到本规范后，按以下顺序执行文档治理：

### 第一步：对照自查

使用 [治理自查清单](template/docs-governance-checklist.md) 确定本仓差距——哪些缺、哪些不合规。

### 第二步：整改 README

按 [README 模板](template/README-template.md) 重写 README。优先补相关文档链接（指向仓内 docs），其次补定位和特性段落。

### 第三步：调整目录结构

- `documents/` 改名为 `docs/`（如适用）。
- 按 Diátaxis 四类创建子目录（tutorial、how-to、reference、explanation）。
- 删除临时文件（如 .tmp、.bak）。
- 内部设计文档移入 `design/` 目录（如有）或添加导航链接。

### 第四步：迁移已有文档

将已有文档移动到对应的 Diátaxis 类别目录中。此步只移动和改名，不重写内容。参考迁移映射：

| 当前位置 | 目标位置 |
| -------- | -------- |
| 基础功能/接入大模型.md | tutorial/01-connect-llm.md |
| 基础功能/自定义工具.md | how-to/custom-tool.md |
| 高阶用法/MCP工具.md | how-to/configure-mcp.md |
| 高阶用法/上下文引擎.md | explanation/context-engine.md |
| API文档/ | reference/ |

### 第五步：补充缺失项

- 缺 Tutorial 的仓：从 README 中分流快速开始内容到 docs/zh/tutorial/。
- 缺 How-to 的仓：从 README 中分流部署指南内容到 docs/zh/how-to/。
- 缺 Reference 的仓：SDK 仓补类级 API 文档；服务仓导出 OpenAPI 规范为独立文档。
- 缺 examples 的仓：新建 examples/ 目录加入门示例。

### 第六步：自查达标

用 [治理自查清单](template/docs-governance-checklist.md) 逐条核对，确认达标。

## 治理机制

【规则】责任到 SIG：每个 SIG 对自己仓的 docs 负责。sig-docs 管总站加规范加跨仓一致性，不替各仓写文档。

【规则】文档随 PR：功能 PR 必须带文档更新，CI 卡控。

【规则】双语主从：中文权威源、英文跟随，CI lint 校验。

【规则】模板化：以 agent-studio studio-2.0 为标杆模板，各仓参考 [README 模板](template/README-template.md) 和 [目录结构模板](template/docs-directory-structure.md) 执行。
